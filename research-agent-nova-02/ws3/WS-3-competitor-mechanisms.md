# WS-3 — Competitor Mechanisms: Proof, Validation & Market Gaps

**Scope:** Source set B = `competitor-research/` (XBOW, FireCompass, Escape); Source set D = public web, used only for competitor claims and always with URL. Read-only analysis; no exploit reproduction, no payloads — mechanisms and capability labels only. Uncertain items marked [UNVERIFIED]; absences stated as "not found / not public," never as speculation about internals.

## 1. Capability comparison

| Capability | Competitor mechanism + source | Gap |
|---|---|---|
| Multi-step exploit chaining | **XBOW:** 5-stage Learn→Map→Coordinate→Attack→Prove loop; "thousands of agents" chain discrete bugs into full attack paths (Moderna: API key→SQLi→IDOR in <18h) [COMPETITOR: `competitor-research/COMPARISON.md` L13, L15; `xbow/pages/page-https-xbow-com-platform.md`]. **FireCompass:** MITRE ATT&CK-aligned graph; credential reuse, app-to-app, app-to-network and app-to-identity/AD lateral movement; chains of 30–100+ steps held in a structured state store, not model context (`firecompass/pages/page-https-firecompass-com-ai-penetration-tes.md` L39). **Escape:** Cascade orchestrator/coverage/exploitation/reporter roles; business-logic chains across multi-identity sessions; findings compound into CI regression tests (`escape/pages/page-https-escape-tech-blog-introducing-casca.md`). | Chaining is table stakes across all three (COMPARISON.md L118). Differentiation now sits in *what* gets chained (business-logic chains — Escape; network/identity — FireCompass) rather than whether chaining exists. |
| Deterministic validation / proof gate | **XBOW:** independent "validator" agents — sometimes LLM peer review, sometimes **custom programmatic checks**; for XSS a headless browser visits the target and confirms the JS payload actually executed (`xbow/pages/page-https-xbow-com-blog-top-1-how-xbow-did-i.md` L47; `xbow/dossier.md` L82). Validators explicitly framed as eliminating "false positives from AI hallucination" (`xbow/pages/page-https-xbow-com-platform.md` L32). **FireCompass:** four-stage validation pipeline — hypothesis → live execution → **signature evaluation** → evidence assembly; each finding checked against an "exploitation signature," ambiguous results re-tested, failures discarded; plus a "deterministic safety gateway" where "a non-deterministic LLM is controlled by deterministic, rule-based systems, never by another model" (`firecompass/pages/page-https-firecompass-com-ai-penetration-tes.md` L91–93). **Escape:** independent "Reporter" agent re-reproduces every finding before filing (`COMPARISON.md` L14); for LLM-surface checks, verification is "deterministic with canary matches, schema-shape regex, and **out-of-band callbacks** instead of one model grading another" (https://escape.tech/blog/llm-security-testing-mcp-pentesting/). | XBOW's validator layer is *partly* LLM-based by its own description — i.e. not fully deterministic ([COMPETITOR] `xbow/dossier.md` L82: "sometimes an LLM, sometimes a custom programmatic check"). FireCompass comes closest to a pure deterministic oracle ("exploitation signature" + deterministic gateway) but the signature spec itself is not public. Escape claims determinism only for its LLM-surface checks; for classic web vulns its gate is a second agent (Reporter) re-reproducing. Out-of-band/DNS-callback proof for *blind* web vulnerabilities is **not found** as a product claim at any of the three — Escape mentions OOB callbacks only in the LLM/MCP context. |
| Client-side / browser-executed proof | **XBOW:** headless-browser validation is a published, named mechanism: "a headless browser visits the target site to verify that the JavaScript payload was truly executed" (https://xbow.com/blog/top-1-how-xbow-did-it); public case studies show `victim-goto` triggering an `alert('XSS')` in a headless browser and DOM-level re-checks that a reflection is not HTML-encoded (https://xbow.com/blog/xbow-2fauth-xss, https://xbow.com/blog/xbow-salesforce-xss); platform ships a "steerable headless browser" (https://xbow.com/platform). **Escape:** "Proof of exploitability with screenshots and execution logs" (`escape/pages/page-https-escape-tech.md` L76); DAST evidence includes screenshots + execution logs; multiple isolated browser sessions per identity model the victim (`escape/dossier.md`). **FireCompass:** browser automation and "evidence capture" listed among harness tools (`firecompass/pages/page-https-firecompass-com-ai-penetration-tes.md` L71), but **no public claim found** that a browser executes the payload and the execution is the pass/fail oracle. | Browser-executed payload as a *published, buyer-visible validation standard* exists at XBOW only. FireCompass: not found. Escape: screenshots/logs evidence, but the browser executing the payload as the acceptance gate is not publicly specified. |
| Chained exploitation with proof artifact | **XBOW** "case file": chained attack path, working exploit, full decision/tactic log, remediation — "nothing hidden behind a severity score" (`xbow/pages/page-https-xbow-com-platform.md` L42). **FireCompass:** "no exploit, no alert" gating; every finding ships working PoC + reproduction steps (`firecompass/pages/page-https-firecompass-com-adversarial-exposu.md` L155). **Escape:** request sequence + user scopes + working exploit + reasoning logs (`COMPARISON.md` L23). | All three ship exploit-attached proof; the artifact *format* differs (case file vs. req/resp+PoC vs. reasoning log) — no market-standard evidence schema exists (see §2). |
| Business-logic / authorization depth | **Escape:** flagship — BLST algorithm, 140+ scenarios, multi-user/session testing for BOLA/IDOR (`escape/external-research.md` L46). **XBOW:** IDOR appears in chains/trace library but not marketed as a methodology; Rawsec critique says XBOW mostly automates classes DAST already catches (`xbow/external-research.md` L173). **FireCompass:** "business-logic abuse" named, not a headline specialism (`COMPARISON.md` L20). | Race conditions and complex multi-step business-logic abuse are flagged industry-wide as only partially covered (`COMPARISON.md` L121) — "not found" as a tested class at all three. |

## 3. Market gaps

| Gap | Why buyer cares | Evidence competitors lack it (source or "not found") |
|---|---|---|
| Independently audited false-positive / benchmark claims | Every headline number in this category is vendor-self-reported; buyers currently must trust marketing (COMPARISON market takeaway #2: "Independent verification is the market's biggest unmet need"). | All FP rates (XBOW "near-zero", FireCompass <2%, Escape ≤4%) self-reported; even press coverage republishes vendor releases — "nearly every headline claim is self-reported" [COMPETITOR] `COMPARISON.md` L119. FireCompass's XBEN report is gated (`firecompass/pages/page-https-firecompass-com-xben-benchmark-rep.md`). Escape's Doyensec benchmark is closest to neutral but "methodology/independence not fully verified" (`COMPARISON.md` L31). |
| Fully deterministic oracle for *classic* web findings (no LLM in the accept/reject path) | "LLM proposes, deterministic oracle disposes" — a second agent re-checking an agent's output is still probabilistic; buyers gating builds on results need pass/fail that cannot hallucinate. | XBOW validators are explicitly "sometimes an LLM" (`xbow/dossier.md` L82). Escape's web-vuln gate is the Reporter *agent* (`COMPARISON.md` L14) — determinism claimed only for LLM-surface checks (canary/schema-regex/OOB, https://escape.tech/blog/llm-security-testing-mcp-pentesting/). FireCompass's "exploitation signature" is deterministic in framing but the signature mechanism is not public — [UNVERIFIED] how signatures are defined per class. |
| Out-of-band callback (DNS/HTTP) proof for blind vulnerabilities (blind SQLi, blind SSRF, XXE) | Blind classes are exactly where scanners and LLM agents produce the most false positives; an OOB canary firing is machine-checkable ground truth. | **Not found** as a product claim at XBOW, FireCompass, or Escape for web testing. Only mentions located: an XBOW *trace narrative* describing OOB technique as an attack step (`xbow/pages/page-https-xbow-com-platform.md` L173), and Escape's OOB callbacks scoped to LLM/MCP checks only (URL above). |
| Browser-executed payload as published acceptance gate beyond XSS | Client-side classes (DOM XSS, CSRF, postMessage, OAuth redirect flows) can only be proven by a browser actually executing behavior — buyer-visible proof standard, not internal plumbing. | XBOW publishes it (headless-browser payload-execution confirmation, https://xbow.com/blog/xbow-salesforce-xss) — partially owned. FireCompass: not found. Escape: screenshots/execution logs but no public browser-execution gate. Gap is *standardization*: no competitor ties every client-side finding class to browser execution as a stated report contract. |
| WebSocket testing as a product surface | Real-time apps (chat, trading, collaboration) are untested by HTTP-only crawlers; endpoints are invisible to OpenAPI-driven scanners. | **Not found** as a product capability at any of the three. Only trace: Escape's *research* methodology models "REST/GraphQL/WebSocket endpoints" (`escape/pages/page-https-escape-tech-blog-methodology-how-w.md` L55) — not a shipped product claim. FireCompass, XBOW: no WebSocket claim found. |
| Race-condition / TOCTOU / concurrency testing | Payment, inventory, voting and quota flows fail under concurrency; class is repeatedly named as underserved even by the specialists. | "Race conditions … only partially covered industry-wide" [COMPETITOR] `COMPARISON.md` L121; Rawsec critique names race conditions as a class XBOW doesn't reach (`xbow/external-research.md` L173). FireCompass, Escape: no race-condition test claim found. |
| GraphQL depth outside Escape | GraphQL introspection/aliasing/batching/resolver abuse breaks generic HTTP fuzzing; most buyers with GraphQL have no real coverage. | Escape owns it (100+ native tests, `escape/pages/page-https-escape-tech-blog-escape-vs-invicti.md` L49). XBOW: one trace ("IDOR in a GraphQL API") but "not a distinct GraphQL specialism" (`COMPARISON.md` L18). FireCompass: named API capability, GraphQL specialism not found. |
| AI/LLM/MCP application testing as shipped product | LLM apps and MCP servers are the newest attacker surface; buyers need it inside the same continuous pipeline, not a separate point tool. | Escape has public productized claims (six OWASP-LLM checks inside normal scans, MCP endpoint discovery, deterministic canary verification — https://escape.tech/blog/llm-security-testing-mcp-pentesting/, Aug 26 2026; guardrail-bypass case study `escape/pages/page-https-escape-tech-blog-how-cascade-explo.md`). FireCompass: only a related gRPC/MCP blog *image* (`firecompass/pages/page-https-firecompass-com-shipped-to-the-bro.md` L90) — no capability claim found. XBOW: publishes buyer guidance ("RFP for AI application pentesting", `xbow/pages/page-https-xbow-com-blog.md` L105) but no product claim found. Escape is the vendor to beat here; the shared gap is that two of three have *nothing*, and Escape's claims are vendor-published only. |
| SSO/multi-tenant auth coverage made explicit | Enterprise targets live behind SAML/OAuth/SSO and multi-tenant isolation; unauthenticated scanning proves little for those buyers. | Escape: explicit — "Built for modern auth: OAuth, SSO, multi-tenant" (`escape/pages/page-https-escape-tech.md` L74), OAuth/SAML/TOTP MFA logins (`escape/dossier.md` L81). FireCompass: MFA flows + app-to-identity chaining (`firecompass/dossier.md` L45). XBOW: SSO appears only as an *admin/console* feature in its Enterprise tier (`xbow/external-research.md` L62); target-authentication mechanisms not public — not found. |
| Evidence schema / reproducibility contract across the industry | Auditors and tooling need machine-checkable, uniform proof; today each vendor invents its own artifact (case file vs. PoC+req/resp vs. reasoning log). | No shared standard found; formats diverge per `COMPARISON.md` L23. Closest to tamper-evidence: FireCompass's append-only timestamped log; no competitor offers an open, third-party-reproducible evaluation methodology (`COMPARISON.md` L119). |
| Transparent pricing | Universal sales-gate friction, called out as customer friction in the market takeaways. | "None of the three publishes real enterprise pricing" [COMPETITOR] `COMPARISON.md` L122 (row L29: all ❌). |

**Where the public claims STOP (Q5, consolidated):**
1. **Signature/oracle internals:** FireCompass never publishes how an "exploitation signature" is defined per vulnerability class; XBOW never publishes which validators are programmatic vs. LLM. Mechanism claims stop at the marketing label.
2. **Independent replication:** no third-party re-run of any FP rate; FireCompass's benchmark report is gated; XBOW disclaims its own original benchmark as "outdated" (`COMPARISON.md` L78).
3. **FireCompass candor is lowest:** "marketing is uniformly upbeat; site shows internal inconsistencies (false-positive rate…) rather than self-critique" (`COMPARISON.md` L83) — treat its <2% as the least-corroborated number.
4. **XBOW scope wall:** web apps + APIs only; network/AD/cloud explicitly excluded; its own blog concedes LLMs "not quite ready" for hardened real-world native-code targets (`xbow/pages/page-https-xbow-com-blog-dead-letter-cve-2026.md` L103).
5. **FireCompass scope wall:** explicitly "does not compete" on static/code analysis (`firecompass/pages/page-https-firecompass-com-ai-penetration-tes.md` L102).
6. **Escape scale wall:** ~29 people across four product lines (`COMPARISON.md` L114); no CVE portfolio at XBOW's scale; no published WebSocket, race-condition, or OOB-blind-class coverage.
