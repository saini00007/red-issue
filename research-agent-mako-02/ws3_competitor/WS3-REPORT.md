# WS-3 Competitive Synthesis — Abhedi Red vs. XBOW / FireCompass / Escape

## 1. Market-Gap Bottom Line

Across all three competitors, **proof-of-exploit is now table stakes** — every vendor leads with "no exploit, no alert," a working PoC per finding, and a sub-single-digit (self-reported, un-audited) false-positive rate. Abhedi already holds structurally *stronger* mechanism on two axes competitors only approximate: **deterministic pure-Python oracle validation** (no LLM in the confirm path; ON by default) and **live-Chromium client-side execution proof of three classes** (DOM-XSS, prototype-pollution, storage-leak; ON by default) — depth no competitor matches. Abhedi's real exposure is **packaging and program machinery, not core exploitation**: its flagship chained-exploitation storyline and executed-chain narrative are behind default-OFF flags, it publishes no buyer-visible benchmark despite owning the harness, and it lacks the surrounding program layer (EASM discovery, CI-regression persistence, compliance-mapped audit trail, published third-party proof) that competitors sell as the product. The defensible whitespace is to *switch on and package* the deterministic + client-side proof it already has, and to publish the benchmark it already runs.

## 3. Buyer-Visible Proof Standards Abhedi Should Match

These are the demonstrable buyer-facing standards competitors set (verbatim-verified where marked HIGH by the web reader):

1. **Working, reproducible exploit per finding under a "no exploit, no alert" gate** — buyer never sees an unvalidated maybe. (XBOW "validates every finding with a working exploit"; FireCompass "working Python PoC + steps + full evidence"; Escape "proves every finding.") *Abhedi has proof capsules but the enforcement gate is default-OFF.*
2. **Independent, de-biased re-verification before filing** — Escape's isolated Reporter agent re-reproduces on the live target; XBOW's independent validators. *Abhedi's oracle set is functionally the de-biased verifier — but it must be named and foregrounded.*
3. **Disclosed false-positive rate as the headline trust metric** — FireCompass "<2% vs 40–70% scanners," Escape "≤4% / +63% more complex TPs." *Abhedi should publish an FP number from its own benchmark harness.*
4. **Re-runnable PoC handed to the customer** — FireCompass ships ready-to-run Python; Escape shows request sequence + user scopes so the buyer can replay the authz break.
5. **Full attack-path / kill-chain with a decision/reasoning log as a first-class artifact** — XBOW case file, Escape full reasoning logs. *Abhedi's richest narrative is behind a default-OFF flag.*
6. **Negative control in the proof** — Escape shows the *rejected* forbidden attempt alongside the successful one to prove a genuine logic flaw, not an accepted parameter.
7. **Fully auditable coverage** — every endpoint/page/asset discovered surfaced, so the buyer sees what was and was not assessed.
8. **Business-context severity + code-owner routing** — Escape's exploitability + data-sensitivity + asset-exposure funnel (off pure CVSS) with the owning team attached.
9. **Compounding regression artifact** — Escape turns each proven finding into a CI/CD regression test re-running every release (durability, not a point-in-time PDF).
10. **Published benchmark transparency** — first-attempt scored **separately** from bounded-retry, single fixed model disclosed, black-box, hint-free, FP-inclusive, mapped to OWASP APTS. *Note: XBEN is reported saturated as of mid-2026 ("a percentage with no context is marketing, not evidence") — Abhedi should publish protocol + FP + hint-free confirmation, not a bare %.*
11. **Third-party / head-to-head corroboration** — Escape's Doyensec-adjacent comparison; XBOW's named real-world CVEs + HackerOne #1. Buyers increasingly discount purely self-scored numbers — the market's single biggest unmet need.
12. **Compliance-mapped, append-only, cryptographically-timestamped audit trail** — FireCompass (PCI DSS 4.0 / SOC 2 Type II / DORA / ISO 27001); Escape "SOC 2 evidence in hours."
13. **Governance-as-proof** — demonstrable scope enforcement, per-host rate limiting, environment-tagged creds, safe-payload (no Modify/Update/Delete) defaults, kill switch — positioned as what makes autonomous testing safe to run in prod.
