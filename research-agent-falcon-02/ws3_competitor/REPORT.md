## A. QUESTION LIST

1. **CHAINED EXPLOITATION — what mechanism turns a confirmed primitive into a later capability?**
   Nobody in this market publicly ships a capability-token or attack-graph mechanism: across the *entire* `competitor-research/` corpus, `attack graph`, `capability token`, `OOB`, `interactsh`, `dnslog` appear **0 times**, and `out-of-band` appears **exactly once** (an xBow trace where the OOB probe *failed*). What competitors *do* describe is: an **orchestrator/coordinator holding engagement state plus a shared knowledge store**, so "one agent's discovery shapes what the next one tries" (Escape), and a **trigger rule where chaining fires on a confirmed finding** (FireCompass). xBow describes chaining only as a capability of agents ("reason through and chain vulnerabilities") plus narrated case-study chains. **Abhedi Red is AHEAD here** — it is the only one with an explicit capability algebra where the LLM is out of the chain path.

2. **DETERMINISTIC VALIDATION — what proof standard do they claim?**
   All three claim *executed* proof and all three resolve verification with an **LLM or an agent-written assertion**, not a registered deterministic oracle: xBow's validators are "sometimes… a large language model; in other cases, we build custom programmatic checks" and its showcased proof is a differential response assertion the agent itself wrote (`return 'Invalid padding' not in response.text`); Escape's Reporter agent is an LLM agent that "independently reproduces each one on the live target"; FireCompass says only that findings are "executed safely against the live target and confirmed before it reaches your dashboard." **No competitor publicly claims a fired-oracle standard. Abhedi Red is AHEAD**, though its one LLM-based independent re-production step is conditional and skipped for some callers.

3. **CLIENT-SIDE PROOF — what do they claim for browser depth and execution-based proof?**
   Thin and shallow relative to the marketing. The single concrete claim is xBow's: "a headless browser visits the target site to verify that the JavaScript payload was truly executed." Escape's client-side claim is *multi-identity* ("several user identities at the same time, each in its own isolated browser session") rather than *execution proof*. Artifact-as-evidence is mostly unimplemented publicly: Escape accepts HAR imports but describes no per-finding screenshot/HAR proof; xBow's trace shows agent commentary + code, not rendered evidence. **Abhedi Red is AHEAD on mechanism** (in-page sink-level canary instrumentation, i.e. actual in-page execution detection, not just "visit the site") and **BEHIND on artifact delivery** (per-finding screenshot-at-execution is an explicit deferred TODO).

4. **BUYER-VISIBLE PROOF STANDARDS — what do reports/customer stories demonstrate as deliverables?**
   A **trace, a chain, and a third-party adjudicator**. xBow ships "a complete, reproducible trace: the chained attack path, the working exploit, and a full log of every decision and tactic," rendered as an interactive trace UI with numbered versioned artifacts (`trace/…/3.bash`, `/12.python`, `/90.python`); its Moderna story demonstrates a 4-link chain (source-leaked API key → authenticate → SQLi primitive → auth-gateway cascade → IDOR) plus the buyer outcome ("resolved within 24 hours of discovery"); and its strongest proof is *third-party triage* ("every submission was confirmed by the program owners"). Escape ships request-by-request attack chains, full orchestrator reasoning logs, and **proof promoted into permanent CI regression tests**. FireCompass ships steps-to-reproduce + request/response pairs + ready-to-run Python + "append-only audit logs with cryptographic timestamps." **Abhedi Red is materially BEHIND**: its report narrative layer is a 5,965-byte LLM prompt merger, and it has **no cross-release re-test/regression mechanism**.

## C. GAP LIST — where Abhedi Red is genuinely BEHIND, ranked by buyer-visible proof value

### G1 — No proof→regression (cross-release retest) loop. *Buyer value: highest.*
Competitors ship proven findings as **permanent, re-run tests**; Abhedi Red's ledger dies with the scan.
- Escape: "Findings flow into Escape DAST, becoming an unlimited regression test that re-runs on every release inside CI/CD" — `escape/pages/page-https-escape-tech-blog-introducing-casca.md`. Positioning: "A report is not a program." same file.
- FireCompass: "One-click revalidation to confirm fixes" + Day-1 CVE validation — `firecompass/pages/page-https-firecompass-com-adversarial-exposu.md`.
- xBow: "on your own release cadence" via API/webhooks — `xbow/pages/page-https-xbow-com-platform.md`.
- Abhedi Red: `ledger/` cells and `chain_node` rows are `scan_id`-scoped (`src/scanner/agent_runtime/finalize.py:65-66`). No re-test/regression mechanism found.
**Mechanism implication:** Abhedi Red has all the ingredients for a regression test (deterministic oracle builders + parsers in `exploit_floor.py` + OOB registry) but has no *persistence* of a proven finding as a re-executable, cross-scan assertion. The gap is a store-and-replay layer over an existing oracle set, not new detection. This is the single most citable differentiator available, and it is currently unbuilt.

### G2 — No first-class buyer-facing trace artifact. *Buyer value: very high.*
- xBow: "Every finding is a complete, reproducible trace: the chained attack path, the working exploit, and a full log of every decision and tactic the agents took. Nothing is hidden behind a severity score. You see the whole kill chain." Rendered as an interactive trace UI with the agent's own commentary interleaved with numbered, versioned artifacts (`3.bash`, `12.python`, `24.python`, `54.python`, `78.python`, `90.python`) — `xbow/pages/page-https-xbow-com-platform.md`.
- Escape: "reasoning logs capture the orchestrator's full chain of thought at every step, and attack chains lay out the reproducible path — not 'we observed exposed PII,' but 'here is exactly how user A read user B's order,' request by request" — `escape/pages/page-https-escape-tech-blog-introducing-casca.md`.
- Abhedi Red: `src/scanner/reporting/narrative.py` is 5,965 bytes — `build_narrative_prompt` (`:45`) + `merge_report_addons` (`:68`). It is an LLM prompt over `findings/effort/rollup`, i.e. **prose generation**, which is exactly what the product thesis says must never be the thing that confirms. `Chain.narrative` (`chain/service.py:49`) is the closest thing.
**Mechanism implication:** the machine-checkable trace already exists in Abhedi Red (executed command, response, oracle verdict, evidence refs) but is *not* the report's primary object. Competitors make the trace the deliverable. This is a rendering + schema gap, not a detection gap — cheap to close, high perceived value.

### G3 — Per-finding visual proof is unimplemented. *Buyer value: high.*
- xBow demonstrates per-step artifacts including actual agent code and server responses, and Escape ships "the exact request sequence, the user scopes involved, the working exploit" with "visual evidence" as a stated DAST benefit — `xbow/pages/page-https-xbow-com-platform.md`; `escape/pages/page-https-escape-tech-product-dast.md` ("Engineers actually fix what they find — Context-rich findings with visual evidence").
- Abhedi Red, honestly: **HAR-slice per finding IS implemented** (`sync_har_proof`, `browser_ingest.py:394-315`, wired at `finalize.py:310`) and evidence rows can carry `screenshot`/`har`/`oob_token` (`finalize.py:612`), with a screenshot streaming API (`scans.py:867`). **But** the gallery is explicitly scan-level, "NOT one finding-linked row per screenshot… a crawl of the homepage is not proof of any finding" (`browser_ingest.py:311-315`), and the finding-level visual is a known gap: "TODO (live-capture seam, deferred): DOM/stored-XSS pop screenshot at the /instrument hit, and the function-level-authz admin response rendered under a low-priv session" (`browser_ingest.py:397-399`). Two separate call sites also describe a "browser-disabled default" (`browser_ingest.py:318,395`).
**Mechanism implication:** the instrumentation already *knows* the exact instant and sink of execution (`browser_server.py:380-383`). Capturing a screenshot at that moment — the seam the TODO names — converts Abhedi Red's strongest mechanism (sink-level in-page canary) into a buyer-visible artifact that neither Escape nor FireCompass demonstrably ships.

### G4 — No external adjudicator, no published benchmark. *Buyer value: high, and the market's weakest link.*
- xBow: ~1,060 submissions where "every submission was confirmed by the program owners and triaged as real, actionable security issues" (`top-1:56,52`); a 104-task benchmark commissioned from outside pentest firms, open-sourced at `github.com/xbow-engineering/validation-benchmarks`, 85% success — **now self-disclaimed**: "These benchmarks were published in 2024. They are now outdated and should no longer be used to measure offensive performance" (`blog-benchmarks.md:28,38,42`).
- FireCompass: XBEN 104/104 with a disclosed protocol — "a single fixed frontier model held identical across all 104 challenges, with first-attempt scoring reported separately from retries so the number can be checked, not just trusted" — plus safety "mapped to the OWASP Autonomous Penetration Testing Standard" (`xben-benchmark-rep.md`).
- Escape: head-to-head on Juice Shop/Fider/Photoview naming Claude Code, Aikido and xBow — and on Photoview reports xBow at **5** findings (High 2) vs Cascade white-box 28 (`introducing-casca.md:116-121`). Methodology was not published ("We'll provide the complete benchmark in a week", `:173`).
- Independent counter-evidence `[INDEP]`: a plain Codex CLI/GPT-5 baseline solved **70–81 of 104** of xBow's own benchmark, and MAPTA reached 76.9% — `xbow/external-research.md`. FireCompass: "No independent teardown, source-code review, or academic paper analyzing FireCompass's internal architecture was found" — `firecompass/external-research.md`.
**Mechanism implication:** nobody in this market has a third-party-auditable proof standard; every headline number traces to vendor PR. Abhedi Red's deterministic-oracle design is *exactly* the property that makes an external audit tractable (a third party can re-fire a stored oracle and get a verdict) — but that value is unrealised with zero published evidence of it. Cheapest high-value gap on this list.

### G5 — No governance/audit-trail artifacts framed for compliance. *Buyer value: medium.*
- FireCompass: "append-only audit logs with cryptographic timestamps," scope allowlists, rate limits, kill switch, "credential scope guards, RBAC," mapped to "PCI DSS 4.0, SOC 2 Type II, DORA, and ISO 27001" (`adversarial-exposu.md:135,116-121`).
- xBow: "Observable and Auditable. Every action the agents take is logged and reviewable"; "40+ leading compliance frameworks"; SOC 2, ISO 27001, **ISO 42001**, HIPAA, GDPR, PCI DSS, NIS 2 (`platform.md:352-357`).
- Abhedi Red: a ledger with `EvidenceObject`s, evidence refs and an `audit_trail`-ish record exist, but **no append-only / non-repudiation / framework-mapping claim** was found in the cited code. Absent, not thin — a valid "not found in repo" result.

### G6 — No published candor or comparative benchmark. *Buyer value: medium, near-zero cost.*
- xBow's own Head of Security Lab: "The autonomous LLM agent kept working but never reached even a leak" and "I don't think LLMs alone are quite ready to write exploits against real-world software yet… it can solve something CTF-shaped." It also names the missing step Abhedi Red built: "You still need to prove exploitability." — `xbow/pages/page-https-xbow-com-blog-dead-letter-cve-2026.md`.
- Abhedi Red publishes no equivalent limitation statement or head-to-head. Given the thesis, publishing *which* classes its oracle floor cannot decide would be both honest and differentiating.

### G7 — Multi-identity is a mechanism, not a product surface. *Buyer value: medium.*
Escape makes identities a first-class buyer input with a quantified payoff ("a second account typically uncovers 30–50% more issues", "a second account… is the only way to answer 'can user A read user B's order?'"). Abhedi Red has the oracle (`diff_access(by_identity=…)`, `diff_cross_tenant`) and the browser login path, but no engagement-level "supply N principals" contract and no per-identity coverage accounting in the ledger. Escape also ships a genuine BLST/multi-tenant specialism that Abhedi Red's single-vuln-class capability table does not model.

## C-bis. Where Abhedi Red is AHEAD (stated for balance; these are the defensible claims)

1. **A deterministic oracle layer with paired controls is unique in this market.** xBow's validators are "sometimes a large language model" (`top-1:47`); Escape's verifier is an LLM Reporter agent (`introducing-casca.md:68`); FireCompass asserts a gate with no described oracle (`adversarial-exposu.md:53,134`). Abhedi Red: `response_diff(payload, control)` + `parse_time_blind(control_out, payload_out)` + canaries + multi-identity diffs + `ledger._oracle_fired` recording *whether the oracle fired* per cell.
2. **A real, default-ON OOB layer.** `config.py:174,183`; per-payload token registry, control-plane correlation, and a **registration time floor** that prevents pre-scan callbacks from confirming (`oob/service.py:151`). Competitor corpus: one failed attempt, zero mentions of a callback-verification design.
3. **Sink-level browser execution detection, not just "visit the page."** `browser_server.py:354,380-383` attributes the canary to the actual sink. xBow's stated method is a headless browser visiting the target.
4. **Chaining is provably outside the LLM path.** "No LLM is in the chain path (the reason chains rarely fired under a weak model)" — `chain/floor.py:7-8`. No competitor makes a determinism claim about its chain layer; all three describe an orchestrator plus agents.
5. **The strongest *independence* property in the market, and the biggest unexploited one.** Escape isolates its Reporter from exploitation messaging; Abhedi Red structurally prevents unproven findings anchoring chains ("Only VERIFIED, evidenced findings anchor a chain node", `chain/service.py:136-139`). This is what would make an external audit possible (G4) — the asset exists, the evidence doesn't.
